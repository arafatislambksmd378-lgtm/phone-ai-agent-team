# Backend deployment and security (Phase 3)

The API requires a non-placeholder bearer token on **every** bind, including loopback. It refuses to start without one. Generate a random token locally with `python3 -c 'import secrets; print(secrets.token_urlsafe(32))'`; place it in `API_AUTH_TOKEN` using your deployment's protected secret store. Never paste tokens into chat, Git, command-line history, or Android screenshots. The heuristic validator cannot prove entropy; use a cryptographic random generator.

Run `python3 main.py --api --api-host 127.0.0.1 --api-port 8000` for API-only service, or `python3 main.py --with-api --api-host 127.0.0.1 --api-port 8000` for Telegram and API in one process with the same database and engine. Set the usual GitHub, AI provider and Telegram settings in the server's protected environment. Restrict the database, workspace and secret-file permissions; use a dedicated unprivileged service account. API token holders have broad project/repository authority; there is no per-user RBAC. Use a minimally scoped GitHub credential and a dedicated test repository.

Terminate HTTPS with a trusted certificate at a reverse proxy (e.g. Caddy or nginx) and forward only to `127.0.0.1:8000`. Configure the proxy to limit request sizes and rates, strip untrusted forwarding headers, redact Authorization from access logs, and allow only authorized clients. Alternatively use `--tls-cert /path/cert.pem --tls-key /path/key.pem`; TLS 1.2+ is enforced. Firewall the backend from direct network access. External plaintext HTTP is not safe even with a bearer token. Android requires trusted HTTPS except explicitly configured local development addresses.

The setup portal defaults to loopback; if exposed or `WEB_SETUP_TOKEN` is set it requires a strong bearer token. Do not expose it publicly. A browser does not automatically send its bearer token; use a properly authenticated proxy or client. Rotate compromised tokens and restart the service.

**Execution warning:** generated code and pytest are not sandboxed by this application. GitHub execution refuses to publish when tests are disabled, missing or failed. `ALLOW_UNSANDBOXED_PROJECT_TESTS=1` is an explicit opt-in only in a disposable, network/credential/filesystem-isolated environment; clearing subprocess environment variables is not isolation. This limitation blocks a production-readiness claim. Task execution elsewhere in the orchestrator also requires infrastructure isolation; do not run untrusted instructions on a privileged host.

**Phase 4 supersedes the opt-in above:** `ALLOW_UNSANDBOXED_PROJECT_TESTS` no longer enables execution. QA/debugger test execution, workspace commands and GitHub agent execution are blocked until an independently verified isolated worker is integrated. Pipelines requiring these operations can fail; this is an intentional safety limitation, not a successful build.
