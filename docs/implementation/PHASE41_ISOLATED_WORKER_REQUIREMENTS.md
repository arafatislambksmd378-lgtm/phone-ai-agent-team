# Required isolated worker infrastructure — not implemented

The existing backend **does not have a secure worker**, and `execution.isolated_worker_available()` remains false. Do not change that return value or set the old host-execution opt-in. An `unshare` command, allowlist, subprocess timeout, restricted environment or a class named sandbox is not sufficient. This document is a deployment/implementation specification, not evidence that any control exists.

## Minimum infrastructure

1. An independently administered remote Linux worker pool outside the backend host. Each job must run in a newly created, disposable microVM (for example Firecracker with a separately hardened host), with a pinned immutable guest image, unprivileged workload user, no host mounts, no container engine socket, no host credentials, no privileged devices and a fresh encrypted, size-limited ephemeral disk. An equivalent isolation boundary requires independent security review; a shared unprivileged container alone is not accepted as proof.
2. Enforce hard vCPU, memory, process count and ephemeral disk quotas at the host/cgroup and filesystem layer; configure a wall-clock deadline enforced outside the guest, terminate the entire VM and descendants on deadline or cancellation, cap output/log sizes and retain no disk or credential material after cleanup. Restrict VM networking to none by default, including DNS and metadata endpoints; any exception must use an explicit deny-by-default egress proxy, never expose internal control-plane addresses.
3. Authenticate backend-to-worker requests over mutually authenticated TLS with certificate rotation, job-scoped identity, authorization, replay protection and a bounded signed manifest containing repository commit, allowed file paths, command, resource limits, job nonce and expiry. No GitHub, AI-provider, Telegram or backend bearer credentials should be present inside the job. Reject untrusted commands and artifacts unless their intended job policy explicitly permits them. Never execute submitted tests on the orchestrator host.
4. Accept only bounded, validated, secret-scanned inputs and return bounded test logs, exit status and content-addressed artifacts. Treat outputs as untrusted: validate paths, sizes, symlinks and secrets before storing or proposing a patch. A read-only snapshot at an immutable commit must be independent of mutable user workspaces. Repository context may only be sent to an AI provider after explicit informed consent; heuristic secret detection cannot prove safety.
5. Keep tamper-evident job lifecycle audit records outside the VM (identity, timestamps, image digest, manifest digest, quotas, result and cleanup outcome; never credentials, raw private source or unrestricted logs). Enforce job-level idempotency across worker crashes, durable state, replay rejection and cancellation. Explicit approval must bind any write to the repository, branch, immutable source commit, approved diff and target SHA; PR merging must retain existing head-scoped approval checks.

## Verification gates before enabling

A security reviewer independent of the implementer must inspect the host/guest configuration, authenticated protocol and image supply chain, and run reproducible hostile integration tests: attempt filesystem escape, host and backend file reads, credential and metadata-service access, outbound DNS/HTTP, VM-to-VM communication, privilege escalation, namespace and process escape, fork/memory/disk exhaustion, output flood, timeout/cancellation bypass, symlink/archive traversal, malformed manifests, replay, impersonation and cleanup after worker crash. Observe host cgroup/network metrics and prove residual VM disks, sockets and processes are removed. Verify no credentials appear in logs or job artifacts. Keep execution blocked if any test cannot be verified or fails.

This sandbox has no Docker/Podman, hypervisor device, remote worker endpoint, worker certificates or configured isolated worker, so those controls cannot be installed or demonstrated here. A dedicated operator-provided worker host/pool, identity/PKI, protected artifact storage, metrics/audit service and reviewed microVM images are required. In addition, a dedicated GitHub test repo, a live model provider configured out of band, and an authorized test bot/account are required for the requested live end-to-end evidence. None of these is assumed available.
